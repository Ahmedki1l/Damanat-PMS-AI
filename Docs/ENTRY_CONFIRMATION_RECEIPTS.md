# Durable successful entry confirmations

Local implementation, not deployed. `ENTRY_V2_CONFIRMATION_RECEIPTS_ENABLED` defaults to false. The additive Alembic revision `e8a24c91d607` follows `d7f3a91c4be2` and is available through the existing Alembic migration path. Current application startup calls `create_tables()` (`Base.metadata.create_all`), not `run_migrations()`; the registered receipt model also permits this additive table to be created at startup. Both paths use binary decision-ID collation on SQL Server. Verify the target table before enabling the flag. This task has not executed production migrations. Disabling the flag restores legacy confirmation reconciliation and retains receipt rows. Automatic schema downgrade is intentionally refused to preserve durable audit records; application rollback keeps the additive table.

In authoritative mode, successful confirmed decisions write a receipt in the same transaction as the entry log and parking session. The decision ID is unique and the complete validated request is fingerprinted (timestamp normalized to facility-local time). Camera, plate, and decision application locks serialize concurrent confirmation work. No successful response is sent until commit returns.

A retry with the same decision and fingerprint returns the original log/session IDs. It reports `duplicate` while that visit remains open, or `stale_after_exit` if SQL says the visit ended. The stale result tells VA not to publish a live identity; it never reopens a session. Reusing an ID with different content returns HTTP 409. Missing receipt storage or failed persistence raises an error and rolls back the transaction; it does not fall back silently. Previous decisions without receipts retain legacy camera/plate/time reconciliation.

The receipt table covers successfully applied confirmed decisions only. Abstentions, shadow observations, stale/superseded refusals, and invalid requests retain existing response behavior; durable VA decision storage owns their retention. No historical backfill or customer data deletion is performed.

Verification: 42 focused tests pass, including a file-backed SQLite store reopened through a fresh engine after a simulated lost response and completed exit, changed-content rejection, atomic rollback/retry, and applying the additive migration before a confirmation. SQLite fixtures replace production application locks; they do not prove SQL Server concurrency, collation, migration execution, or a killed production process. Those require a target-stack test before activation. Receipt retention follows entry/session audit retention; no automatic purge is implemented.

The new foreign keys deliberately prevent deleting an entry log/session still referenced by a receipt. Existing one-off cleanup scripts (`scripts/setup/cleanup_test.py`, `scripts/setup/clean_invalid_plates.py`) can therefore fail on referenced rows after activation. Retention/cleanup must account for receipt ownership; this task does not change or run those scripts.
